# План проекта: добровольное отслеживание маршруток

Документ для команды, которая планирует первую версию сайта. Здесь описана предлагаемая архитектура и порядок работ, а не окончательно выбранные технологии: решения о карте, правилах публикации координат и возможностях сайта нужно подтвердить всей командой до написания кода.

## 1. Проект простыми словами

Водитель входит на сайт, выбирает назначенный ему маршрут и нажимает «Начать передачу». Браузер спрашивает разрешение на геолокацию телефона. После согласия сайт периодически получает координаты и отправляет их на сервер. Сервер проверяет данные и сообщает актуальное положение пассажирским страницам. На карте пассажира появляется значок маршрутки с номером маршрута и временем последнего обновления.

**Поток данных:** телефон водителя → браузер водителя → сервер проекта → браузер пассажира → карта с меткой.

Карта — это не то место, где водитель «передаёт GPS». Карта рисует основу улиц и поверх неё значки. Геопозиция отдельно поступает в браузер с устройства, затем передаётся на наш сервер.

## 2. Рекомендуемое решение для первой версии

| Часть | Предложение | Зачем |
|---|---|---|
| Сайт водителя и пассажира | HTML, CSS и JavaScript; при необходимости позже TypeScript | Код в браузере отвечает за кнопки, запрос геолокации и отображение карты. Браузерный API геолокации вызывается из JavaScript. |
| Сервер | Python + FastAPI | Python вам знаком; сервер принимает координаты, проверяет пользователя и выдаёт данные пассажирам. FastAPI — один из вариантов, а не обязательное требование. |
| Обмен сайт—сервер | HTTPS и JSON; сначала обычные HTTP-запросы | JSON — текстовый формат данных, который могут понимать и JavaScript, и Python. Языки не нужно «склеивать»: они общаются через сеть по согласованным адресам и правилам. |
| Обновление карты пассажира | Для первого прототипа опрос сервера раз в несколько секунд; затем при необходимости WebSocket | Опрос проще реализовать и отлаживать. WebSocket позволяет серверу сразу присылать изменения, но требует больше работы. |
| База данных | PostgreSQL; PostGIS — если появятся сложные географические запросы | Хранит учётные записи, маршруты, назначения водителей и последнее положение. В MVP можно хранить только текущую точку и не собирать историю поездок. |
| Карта | Выбрать одного поставщика и проверить условия использования до разработки | Карта отображается в браузере через JavaScript-библиотеку/API; координаты маршруток накладываются на неё как маркеры. |

Для первого прототипа разумная связка — **JavaScript в браузере + Python/FastAPI на сервере + PostgreSQL + карта одного выбранного поставщика**. Если команда решит иначе, общий поток данных останется тем же.

### Важное про выбор карты

Не выбирайте Google, Яндекс или OpenStreetMap только по внешнему виду. Сравните покрытие нужного города, условия использования, стоимость и лимиты, необходимость ключа/API-ключа, ограничения на хранение или кэширование карт, доступность для пользователей и правила отображения атрибуции. У OpenStreetMap есть данные карты и отдельные публичные серверы тайлов; публичные серверы не следует считать бесплатной инфраструктурой без лимитов для нагруженного рабочего сайта. Зафиксируйте выбор письменно до привязки интерфейса к конкретному API.

## 3. Что происходит при одной передаче координаты

1. **Водитель входит в аккаунт.** Сервер знает, что это водитель, и какой маршрут ему разрешён.
2. **Водитель нажимает «Начать».** Сайт показывает понятное объяснение и запрашивает разрешение браузера на геолокацию. Без разрешения сайт не получает координаты.
3. **Устройство определяет положение.** Источником могут быть GPS, Wi‑Fi, мобильная сеть и другие механизмы устройства. Точность меняется; браузер также сообщает оценку погрешности.
4. **Браузер передаёт точку серверу по HTTPS.** Например, логически это данные вида: идентификатор активной поездки, широта, долгота, точность и время измерения. Пароль в каждой точке не передаётся — запрос использует защищённую сессию/токен.
5. **Сервер проверяет точку.** Проверяет вход пользователя, право работать на маршруте, допустимый формат и диапазон координат, время и частоту запросов. Номер маршрута берётся из назначения на сервере, а не безоговорочно принимается из браузера.
6. **Сервер сохраняет последнее положение.** Для первой версии этого достаточно. Историю пути сохранять только при отдельной необходимости и с понятным сроком удаления.
7. **Пассажирская страница получает актуальные точки.** Сначала она может запрашивать их каждые несколько секунд. Сервер возвращает список активных машин, а не данные аккаунтов водителей.
8. **Код карты ставит или перемещает маркер.** Подпись маркера показывает номер маршрута. При нажатии можно показать время обновления и, если нужно, оценку точности.
9. **Передача прекращается.** Водитель нажимает «Завершить», сервер закрывает активную поездку, а маркер исчезает или становится неактивным. Если связь пропала без нажатия, сервер считает точку устаревшей по тайм-ауту.

## 4. Ключевые вопросы и ответы

### «На каком языке будем писать?»

Для браузерной страницы — JavaScript (позже можно перейти на TypeScript). Для сервера — Python. HTML задаёт структуру страницы, CSS — внешний вид. База данных понимает SQL. Это нормальная ситуация: в одном проекте несколько языков, потому что у каждого своя задача.

### «Как JavaScript и Python будут связаны?»

Не прямым включением одного языка в другой, а сообщениями через HTTP. Браузер отправляет серверу запрос по URL, например смыслом «вот моя новая точка», в JSON. Сервер отвечает тоже JSON: «принято» или «ошибка». Имена полей, адреса запросов и правила ответа команда заранее описывает в API-контракте.

### «Кто получает GPS?»

Координату получает браузер на телефоне водителя через встроенный API геолокации после разрешения. Python-сервер сам не обращается к GPS телефона: он получает уже измеренную точку от сайта.

### «Как точка оказывается на карте?»

Страница пассажира получает широту и долготу от нашего сервера и передаёт их библиотеке карты как положение маркера. Поставщик карты рисует улицы и помогает преобразовать координату в положение на экране. Маршрутная метка — отдельный слой поверх основы карты.

### «Нужны ли WebSocket и постоянное соединение сразу?»

Не обязательно. Для небольшого первого теста проще обновлять список точек по обычному HTTP-запросу раз в 3–5 секунд. Когда станет ясно, что этого недостаточно, можно добавить WebSocket: браузер один раз подключается, сервер сам присылает изменения. Оба варианта дают обновление карты; различается способ доставки.

### «Будет ли сайт передавать координаты, если телефон заблокирован?»

На это нельзя надёжно рассчитывать в обычном мобильном браузере. Операционная система может приостановить вкладку, браузер может перестать часто получать координаты, сеть может пропасть, а батарея — разрядиться. Для первого этапа явно требуйте, чтобы водитель держал сайт открытым; показывайте статус и время последнего обновления. Если непрерывная фоновая работа станет обязательной, отдельно исследуйте установку веб-приложения и/или нативное мобильное приложение и требования магазинов приложений. Это не обещание, что PWA решит ограничения фонового GPS.

### «Какие координаты показывать?»

Широту и долготу устройства, время измерения и оценку точности. Если точность плохая, можно показывать предупреждение или временно не обновлять метку. Сначала лучше обозначить точку, что координаты приблизительные и могут запаздывать.

### «Нужна ли пассажиру регистрация?»

Технически смотреть общую карту можно и без аккаунта. Если по требованиям проекта пассажиры регистрируются, регистрация всё равно может не влиять на передачу координат. Для MVP рассмотрите публичный просмотр карты и отдельную регистрацию водителя с проверкой/подтверждением администрацией — так меньше барьеров для проверки идеи.

### «Как не показывать неверные или чужие данные?»

Сервер назначает водителю маршрут, разрешает только одну активную поездку (если таково правило), проверяет сессию и не принимает номер маршрута как доказательство права. Пассажирскому API отдаётся минимум: номер маршрута, координата, точность и время обновления. Не нужно показывать имя, телефон или постоянный идентификатор водителя.

### «Нужно ли хранить весь путь?»

Для показа текущей маршрутки — нет. Храните последнюю точку и активное состояние, а старые данные удаляйте или заменяйте. Хранение истории увеличивает риски приватности и требования к защите; добавляйте его только при понятной цели, согласии и сроке хранения.

## 5. Предлагаемая структура системы

```text
Телефон водителя
  └─ Браузер: кнопка «Начать», разрешение геолокации, координаты
       └─ HTTPS / JSON → API на Python
                           ├─ проверка пользователя и маршрута
                           ├─ обновление последней точки в PostgreSQL
                           └─ выдача активных точек пассажирам
                                └─ HTTP-опрос (MVP) / WebSocket (позже)
                                     └─ Браузер пассажира
                                          ├─ карта выбранного поставщика
                                          └─ маркер с номером маршрута
```

Файл `Схема трансляции геопозиции.svg` показывает это подробнее, включая блоки безопасности, состояния передачи и условные обозначения. SVG — векторное изображение: его можно масштабировать для презентации и печати без потери чёткости.

## 6. Что должно быть согласовано до разработки

1. **Город и территория теста:** один район, несколько улиц или весь город.
2. **Кто подтверждает водителя:** свободная регистрация, приглашение или ручное одобрение администратором.
3. **Назначение маршрута:** выбирает администратор или водитель; кто исправляет ошибку.
4. **Правило поездки:** когда начинать/останавливать, разрешена ли одна или несколько машин на аккаунт.
5. **Свежесть данных:** пример для обсуждения — обновление при активном сайте каждые 3–5 секунд; после 20–30 секунд без свежих точек показать «данные устарели», позже скрыть маркер. Это начальные пороги для испытаний, не универсальные числа.
6. **Точность:** как поступать с плохой точностью и скачком координат. Не пытаться «исправить GPS» догадками; лучше показать статус или отфильтровать явно невозможный скачок.
7. **Карта и условия поставщика:** покрытие, бюджет, API-ключ, квоты, лицензия и атрибуция.
8. **Приватность:** что видит пассажир, сохраняются ли точки, когда они удаляются, как водитель отзывает согласие.
9. **Устройства:** какие телефоны и браузеры будут в тесте; доступен ли мобильный интернет.
10. **Ожидаемая нагрузка:** сколько одновременно работающих водителей и смотрящих пассажиров.

## 7. Подробный план действий

### Этап 0. Описать правила проекта

- Записать сценарии водителя и пассажира обычными словами.
- Решить, доступна ли карта без входа, кто может начать трансляцию и как водитель назначается на маршрут.
- Согласовать примерные интервалы обновления, устаревания и удаления точки.
- Назначить ответственных: интерфейс/карта, сервер/API, база данных, тестирование и принятие решений.
- Результат: короткое описание требований, на которое команда может ссылаться.

### Этап 1. Нарисовать экраны и состояния

До программирования нарисовать на бумаге или в макете: экран входа водителя, экран выбора/подтверждения маршрута, кнопки начала и завершения, состояния «нет разрешения», «ищем GPS», «передача идёт», «нет сети», «точка устарела»; экран пассажира с фильтром маршрута и маркерами. Продумать, что увидит человек при ошибке, а не только при успешной работе.

**Результат:** несколько макетов и согласованный пользовательский сценарий.

### Этап 2. Проверить карту и браузерную геолокацию отдельно

- Выбрать кандидатов карты и проверить лицензию/стоимость для реального использования.
- На тестовой странице получить одну точку на телефоне только после нажатия кнопки и согласия.
- Проверить разрешение, отказ, слабый сигнал, выключенное определение местоположения, потерю сети и уход вкладки в фон.
- Проверить, что сайт работает по HTTPS. Для геолокации браузер требует защищённый контекст; исключение для разработки обычно — `localhost`.

**Результат:** короткий протокол тестов и выбранный поставщик карты. На этом шаге ещё не строится вся система.

### Этап 3. Согласовать данные и API между участниками

Команда должна одинаково понимать поля, форматы и ошибки. Обсудите логические операции, не привязываясь пока к коду:

- водитель начинает поездку;
- водитель отправляет точку;
- водитель завершает поездку;
- пассажир получает активные точки.

Для точки нужны как минимум: широта, долгота, время измерения и точность. Идентификатор водителя/поездки определяется безопасной сессией, маршрут — назначением на сервере. Согласуйте ответы при истёкшей сессии, отказе в разрешении, неверной координате и отсутствии активной поездки.

**Результат:** API-контракт — таблица запросов/ответов и пример JSON, который смогут независимо реализовать frontend- и backend-разработчики.

### Этап 4. Спроектировать минимальные данные

Для первого обсуждения достаточно сущностей:

- **Пользователь:** учётная запись и роль (водитель, пассажир, администратор).
- **Маршрут:** внутренний идентификатор, отображаемый номер и необязательное название/цвет.
- **Назначение водителя:** какой маршрут водитель вправе транслировать и подтверждён ли аккаунт.
- **Активная поездка/последняя точка:** водитель или поездка, маршрут, широта, долгота, время получения/измерения, точность и активность.

Не начинайте с хранения каждого измерения навсегда. Сначала ответьте, нужна ли история для продукта; если нет — храните только актуальное состояние и предусмотрите очистку неактивных данных.

### Этап 5. Собрать минимальный сквозной сценарий

Сначала сделайте одну тестовую роль водителя и одну пассажирскую карту. Водитель нажимает кнопку, браузер получает разрешение, сервер принимает тестовую точку, пассажир видит иконку с номером маршрута. Затем добавить реальные аккаунты, маршруты, проверки доступа и обработку ошибок. Это уменьшает число неизвестных: сначала доказывается весь путь одной точки, затем — масштабирование.

### Этап 6. Решить способ обновления пассажирской карты

Для первого запуска использовать HTTP-опрос с настраиваемым интервалом (например, 3–5 секунд) и возвращать только активные свежие точки. Измерить задержку, расход сети и нагрузку на сервер. Если обновления становятся слишком тяжёлыми или нужна более мгновенная доставка, добавить WebSocket. Не нужно одновременно внедрять оба механизма без измеримой причины.

### Этап 7. Проверить безопасность и приватность

- Везде использовать HTTPS; не записывать пароли, токены и точные координаты в обычные отладочные журналы.
- Убедиться, что координату отправляет вошедший водитель, а не произвольный посетитель.
- Ограничить частоту отправки и размер/формат запросов.
- Не публиковать личные данные водителя.
- Показать водителю явное состояние передачи и способ остановить её.
- Указать, что координата приблизительна и может запаздывать; пассажир не должен полагаться на неё как на гарантию прибытия.
- Определить срок хранения и доступ к координатам. Проверить требования местного законодательства и правил платформ/поставщика карт.

### Этап 8. Испытать на ограниченной группе

Провести тест в одном районе на нескольких согласившихся водителях и пассажирах. Сверить метку с фактическим положением, проверить задержку, точность, поведение при выключении экрана/вкладки, потере интернета, запрете геолокации, завершении поездки и повторном входе. Собрать замечания, исправить понятность интерфейса и выбрать пороги устаревания на реальных данных.

### Этап 9. Подготовить запуск и поддержку

Перед запуском назначить, кто следит за сервером и квотами карты, куда сообщать о неверной метке, как отключить ошибочный аккаунт и как восстанавливать сервис. Добавить понятное сообщение, если карта/API/сервер временно недоступны. Не объявлять функцию надёжным отслеживанием, пока тесты не подтвердили её работу на целевых телефонах.

## 8. Критерии готовности первой версии

Первый MVP можно считать проверенным, когда:

- водитель понимает, что именно включается, и сам запускает/останавливает передачу;
- запрос разрешения на геолокацию обработан при согласии и при отказе;
- сервер не принимает координаты от неавторизованного пользователя;
- активная точка появляется на пассажирской карте с правильным номером маршрута;
- время последнего обновления видно или понятно по состоянию метки;
- старые координаты не выглядят как текущее положение;
- при потере сети и завершении поездки метка корректно становится устаревшей/исчезает;
- команда проверила поток на реальных телефонах и задокументировала ограничения фоновой работы;
- политика хранения координат и выбранные условия карты понятны команде.

## 9. Слова, которые будут встречаться

- **Координата:** широта и долгота; точка на Земле.
- **Точность (accuracy):** оценка радиуса погрешности, а не обещание, что точка точно в этом радиусе.
- **API:** согласованный способ, которым две программы обмениваются запросами и ответами.
- **JSON:** текстовая запись данных с именованными полями.
- **Backend / сервер:** часть проекта, которая проверяет запросы и хранит/выдаёт данные.
- **Frontend / клиент:** сайт в браузере пользователя.
- **HTTP:** обычный обмен запросами и ответами через интернет; HTTPS — защищённый вариант.
- **WebSocket:** длительное соединение, по которому сервер может отправлять обновления без постоянных отдельных запросов.
- **База данных:** организованное хранилище пользователей, маршрутов и актуальных положений.
- **MVP:** минимальная версия, достаточная, чтобы проверить главную идею с реальными людьми.

## 10. Главное для вашей роли

Ваша ближайшая задача — не сразу писать карту, а подготовить проверяемый план своей части: какие данные карта получает, в каком формате и с какой частотой; как рисуется значок с номером маршрута; как показываются плохая точность и устаревшая точка; что происходит при запрете геолокации или потере сети. После согласования API-контракта можно будет реализовывать отображение независимо от того, написан сервер на Python или на другом языке.
