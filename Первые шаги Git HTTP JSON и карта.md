# Часть 1. Что такое Git и «связь папки с Git»

## 1.1. Представь черновик, список выбранного и фотографии этапов

Git помогает команде хранить этапы изменения файлов, сравнивать их и обмениваться ими.

Упрощённо есть четыре места:

1. **Рабочие файлы** — то, что прямо сейчас открыто и меняется в VS Code.
2. **Staging area / индекс** — список изменений, которые ты собираешься включить в следующий снимок.
3. **Локальные коммиты** — сохранённые снимки изменений на твоём компьютере.
4. **Remote / удалённый репозиторий** — общий сервер команды, например GitHub. Изменения попадут туда только после отправки (`push`).

Схема:

```text
редактирую файл → git add → подготовленные изменения → git commit → локальная история
                                                                  │
                                                                  └─ git push → сервер команды
```

Обратное направление:

```text
сервер команды → git fetch (узнать о новых коммитах) → git pull (получить/объединить изменения)
```

**Commit сам по себе ничего не выкладывает в интернет.** `push` — отдельная команда, которая отправляет коммиты на удалённый сервер. Изменения этой задачи фиксируются локальным коммитом; push на `origin` не выполняется.

## 1.2. Почему одна папка Git, а другая нет

Репозиторий Git обычно содержит скрытую папку `.git`. В ней находятся история, ветки, настройки связи с сервером и индекс изменений. Проверить её наличие в PowerShell можно так:

```powershell
Get-ChildItem -Force
git rev-parse --show-toplevel
```

У тебя есть две папки с файлами проекта:

- `C:\Учёба\Проект\ULTrack` — исходная рабочая копия Git.
- `C:\Учёба\Нейропроект\ULTrack` — целевая копия; в неё перенесены Git-метаданные исходной копии. Поэтому здесь сохранена история, активна ветка `feature-Maksim`, а `origin` указывает на GitHub. Папки имеют отдельные рабочие файлы, хотя используют копию одной и той же исходной истории.

Не запускай в целевой копии `git init` и не меняй remote наугад: репозиторий уже подключён. Перед работой проверь, в какой именно папке выполняются команды (`git rev-parse --show-toplevel`), и не путай её с исходной копией. Изменения этой задачи включаются в локальную историю целевой папки отдельным коммитом; push не делается.

При первоначальной проверке исходного репозитория ветка называлась `feature-Maksim`; `git status` показывал изменения у нескольких файлов и неотслеживаемую `.vs/`, а `git diff` не выводил текстовых различий. Эти особенности исходной папки не исправлялись. Перед любыми действиями в ней заново проверь актуальный `git status` и `git diff`.

## 1.3. Первые безопасные команды

Открой терминал VS Code (**Terminal → New Terminal**, PowerShell), затем перейди в целевую Git-папку:

```powershell
cd "C:\Учёба\Нейропроект\ULTrack"
git rev-parse --show-toplevel
git branch --show-current
git status
git status --short
```

Как читать `git status --short`:

- ` M file.py` — изменённый файл ещё не добавлен в staging;
- `M  file.py` — изменение уже добавлено в staging;
- `?? new-file.md` — новый неотслеживаемый файл;
- `A  new-file.md` — новый файл уже подготовлен к коммиту.

Первая позиция в двухсимвольном статусе показывает staging, вторая — рабочие файлы. Если статус показывает изменения, не надо автоматически их «чинить»: сначала узнай, кто и зачем их сделал.

Показать разницу конкретного файла:

```powershell
git diff -- README.md
git diff -- applist/app/urls.py
```

`git diff` показывает незастейдженные изменения. После `git add` посмотри подготовленное отдельно:

```powershell
git diff --cached
```

Если ты только изучаешь Git, на этом остановись: команды выше только читают информацию.

## 1.4. Обычный сценарий разработчика

Когда команда договорилась, что ты работаешь в Git-копии и рабочее дерево чистое:

```powershell
git switch -c feature/map-demo
```

Это создаёт новую ветку от текущего состояния. Ветка — отдельная линия изменений; она позволяет готовить работу независимо от основной линии команды. Не запускай эту команду поверх чужих незакоммиченных изменений, не выяснив, чьи они.

После редактирования:

```powershell
git status
git diff
git add applist/main/views.py applist/main/urls.py applist/app/urls.py
git add applist/main/templates/main/map.html applist/main/static/main/map.css applist/main/static/main/map.js
git diff --cached
```

`git add` не отправляет файл на сервер. Он говорит Git: «включи именно эти изменения в мой будущий снимок». Можно добавить один конкретный файл, чтобы случайно не включить чужие правки. После просмотра staged-разницы локальный снимок создаётся так:

```powershell
git commit -m "feat: добавить демонстрационную карту"
```

У коммита есть автор, дата, сообщение и ссылка на предыдущую историю. Посмотреть последние снимки:

```powershell
git log --oneline --graph --decorate -10
```

До этого момента снимок существует только локально. В рамках этой работы изменения целевой копии сохраняются локальным коммитом. Push на сервер команды — отдельный шаг; он не выполняется.

```powershell
# Только для понимания: эта команда отправляет коммиты на сервер.
git push -u origin feature/map-demo
```

Не нажимай в VS Code **Sync Changes** без понимания, не делает ли эта кнопка push. Синхронизация обычно взаимодействует с удалённым сервером.

## 1.5. Как устроена связь с GitHub

`git remote -v` показывает сохранённый адрес удалённого репозитория, например `origin`. У настоящей копии он мог быть задан при `git clone`. `git fetch origin` загружает сведения о новых ветках/коммитах, но не переписывает твои рабочие файлы. `git pull` получает изменения и пытается объединить их с текущей веткой. При конфликте Git попросит человека выбрать правильный итоговый текст.

В коротком README есть пример `git pull origin main`, но фактическая ветка при проверке называлась `feature-Maksim`. Значит, прежде чем копировать ту команду, нужно узнать у команды, от какой ветки именно надо получать изменения; не делай pull «на автомате».

Клонирование — это получение проекта вместе с Git-историей:

```powershell
git clone <адрес-репозитория> "C:\Учёба\Новый-клон-ULTrack"
```

В `<адрес-репозитория>` вставляют реальную HTTPS/SSH-ссылку из GitHub/GitLab, а не буквальные угловые скобки. Команда создаёт `.git` внутри новой папки. В текущий каталог `Нейропроект\ULTrack` клонировать поверх уже существующих файлов нельзя; для этого нужна новая пустая папка.

# Часть 2. HTTP, HTTPS и JSON на примере карты

## 2.1. Кто с кем разговаривает

В браузере работают HTML, CSS и JavaScript. Django работает на сервере на Python. JavaScript и Python не подключаются друг к другу как два модуля одного файла: они отправляют друг другу сетевые сообщения.

В нашем демо:

```text
Chrome / Edge
  ├─ GET /                  → Django возвращает HTML страницу
  ├─ GET /static/main/map.css → Django staticfiles возвращает CSS
  ├─ GET /static/main/map.js  → Django staticfiles возвращает JavaScript
  ├─ GET /api/demo/vehicles/  → Django возвращает JSON с точками
  └─ GET https://tile.openstreetmap.org/... → тайловый сервер возвращает кусочки карты
```

Страница сначала содержит пустой `<div id="map">`. После загрузки Leaflet и `map.js` код JS создаёт карту внутри этого блока. Затем `fetch()` запрашивает `/api/demo/vehicles/`. Django запускает URL-маршрут, вызывает Python-функцию `demo_vehicle_locations`, а та возвращает `JsonResponse`. JavaScript читает JSON и создаёт маркеры.

## 2.2. HTTP — запрос и ответ

HTTP — правила обмена запросом и ответом. Пример запроса браузера:

```http
GET /api/demo/vehicles/ HTTP/1.1
Host: 127.0.0.1:8000
Accept: application/json
```

Сервер отвечает, например:

```http
HTTP/1.1 200 OK
Content-Type: application/json

{"mode":"demo","vehicles":[{"id":"demo-1","route_number":"1","lat":54.3142,"lon":48.4031}]}
```

Важные методы:

- **GET** — попросить данные/страницу, обычно не меняя состояние сервера. Так пассажир запрашивает список текущих маршруток.
- **POST** — отправить данные, которые сервер должен проверить и обработать. Так водитель в будущем может отправлять новую точку.
- **PUT/PATCH** — заменить/обновить ресурс; для первого прототипа можно пока не использовать.
- **DELETE** — удалить ресурс; тоже пока не нужен.

Код ответа помогает понять результат: `200` — успешно; `400` — неверные данные; `401` — не выполнен вход; `403` — нет прав/не прошла защита; `404` — адрес не найден; `405` — метод не разрешён; `500` — ошибка сервера.

## 2.3. HTTPS — защищённый HTTP

`HTTPS` — HTTP, передаваемый внутри защищённого TLS-соединения. Обычно браузер проверяет сертификат сайта и шифрует обмен. Это помогает посторонним не прочитать или незаметно изменить пароль, сессию и координаты по пути через сеть.

HTTPS **не** доказывает, что водитель имеет право на выбранный маршрут, не проверяет истинность координаты и не спасает от слабого пароля или ошибки программы. Поэтому нужны и HTTPS, и вход/права, и серверная проверка запроса.

На компьютере разработчика допустим адрес `http://127.0.0.1:8000`: `localhost` считается специальным безопасным контекстом для многих возможностей браузера. На опубликованном домене передачи учётных данных и координат обязаны идти по HTTPS. Браузерная геолокация также требует защищённого контекста (обычно HTTPS; исключение для разработки — localhost) и явного разрешения водителя.

## 2.4. JSON — коробка с именованными полями

JSON — текстовый формат обмена данными. Его могут одинаково разобрать Python, браузерный JavaScript и другие языки.

```json
{
  "mode": "demo",
  "vehicles": [
    {
      "id": "demo-1",
      "route_number": "1",
      "lat": 54.3142,
      "lon": 48.4031,
      "accuracy_m": 25,
      "is_demo": true
    }
  ]
}
```

В этом примере `vehicles` — массив, в массиве один объект; `lat` и `lon` — числа, `route_number` — строка, `is_demo` — логическое значение. Строки в JSON всегда в двойных кавычках. В JSON нет комментариев, `undefined` и завершающей запятой после последнего поля.

В Python Django строит JSON-ответ через `JsonResponse({...})`. В JavaScript `await response.json()` разбирает тело ответа в объект JS. Это не магия и не импорт Python в браузер: обе стороны договорились о форме текста.

Координаты машин наш код передаёт в Leaflet, который рисует маркеры в браузере. Tile-сервер отдельно получает запросы на фрагменты видимой карты. В текущем примере координаты демонстрационных машин не подставляются в URL OSM-тайлов. Для настоящего проекта всё равно изучите политику приватности и условия выбранного поставщика карты.

Проверить API вручную при запущенном сервере можно в браузере: `http://127.0.0.1:8000/api/demo/vehicles/`. В PowerShell:

```powershell
Invoke-RestMethod "http://127.0.0.1:8000/api/demo/vehicles/" | ConvertTo-Json -Depth 5
```

## 2.5. Как будет выглядеть настоящая передача позже

Пока реализован только GET учебных точек. Будущий поток может выглядеть так:

```text
водитель нажал «Начать»
  → браузер запросил разрешение Geolocation API
  → браузер получил latitude, longitude, accuracy, timestamp
  → HTTPS POST /api/driver/location/ с JSON и сессией водителя
  → Django проверил пользователя, назначенный маршрут, диапазон/свежесть/частоту
  → Django сохранил только последнюю разрешённую точку
  → пассажирский браузер делает GET /api/vehicles/ каждые несколько секунд
  → JavaScript двигает существующий маркер, а не создаёт новый поверх старого
```

Пример будущего **формата для обсуждения, не готовый работающий endpoint**:

```http
POST /api/driver/location/ HTTP/1.1
Content-Type: application/json
X-CSRFToken: <токен сессии>

{"lat":54.3142,"lon":48.4031,"accuracy_m":18,"measured_at":"2026-10-27T12:00:00Z"}
```

Сервер не должен доверять тому, что браузер сам прислал `route_number` или чужой `driver_id`. Сервер получает пользователя из защищённой сессии, проверяет его назначение и сам определяет маршрут. Для POST при сессионной авторизации Django нужно сохранить CSRF-защиту. Нельзя добавлять пароль или секретный токен в JavaScript-код страницы: его видит посетитель сайта.

## 2.6. Обычный HTTP-опрос и WebSocket

Пока пассажир сам периодически спрашивает сервер: «Есть новая точка?» Это обычные короткие HTTP GET-запросы. Реализуется проще, прозрачно видно во вкладке **Network** браузера и удобно для маленького MVP. В нашем учебном JS интервал — 5 секунд.

WebSocket держит длительное соединение: пассажир подключается один раз, сервер сам присылает новое положение. Это может снизить задержку/лишние опросы, но требует управления переподключением, авторизацией и несколькими подключениями. Сначала измерьте GET-опрос; не вводите WebSocket до появления конкретной необходимости.

# Часть 3. Как добавить фон карты города

## 3.1. «Загрузить карту» обычно значит подключить онлайн-тайлы

Не нужно копировать целый город картинкой в проект. Интерактивная карта делится на много небольших фрагментов — **тайлов**. При перемещении или масштабировании браузер загружает нужные фрагменты. JavaScript-библиотека показывает их, а поверх располагает ваши данные: метки машин, остановки и маршруты.

Надо различать:

- **Библиотеку-карту/renderer** — отображает фон и объекты в браузере. Здесь это Leaflet.
- **Картографические данные** — улицы, здания, подписи; здесь это слой OpenStreetMap.
- **Хост тайлов / tile provider** — сервер, который отдаёт картинки или векторные данные слоёв.
- **Наши точки** — отдельный JSON от сервера ULTrack, который JS превращает в маркеры.

Leaflet не владеет картами и сам по себе не приносит улицы: в него добавляется слой тайлов выбранного поставщика. Это позволяет позже заменить фон, не переписывая всю логику значков.

## 3.2. Выбор для Ульяновска: отдельная оценка техники и лицензии

### Для учебной карты сейчас

В коде выбран **Leaflet 1.9.4 + стандартный OSM raster tile endpoint**, центр `54.3142, 48.4031` (район центра Ульяновска). Это минимальный способ показать настоящую подложку города и наложить тестовые метки без API-ключа. В карте указана атрибуция OpenStreetMap.

Это годится для локального теста и малого числа ручных просмотров с соблюдением правил tile-сервера. Это **не обещание, что общественный сервер OSM обслужит запущенный транспортный сервис**: у сервиса нет SLA, он работает best-effort, может ограничивать/блокировать неподходящую нагрузку. Запрещена массовая предварительная загрузка тайлов/офлайн-карты. Нужны корректная видимая атрибуция, стандартный HTTPS URL и соблюдение кэш-заголовков.

### Для настоящего запуска

**Рекомендация:** сохранить Leaflet как слой отображения, а до публичного запуска выбрать коммерческого хостера OSM-тайлов с условиями, подходящими для сайта с live-маркерами и ожидаемой нагрузкой, либо развернуть собственный источник тайлов. Письменно проверьте: покрытие Ульяновска, разрешённый тип проекта (включая отслеживание в реальном времени), лимиты, стоимость, SLA, атрибуцию, кэширование, разрешённые домены и сбор/обработку данных. Не делайте тайловый endpoint константой, которую нельзя поменять.

**Яндекс.Карты** могут быть хорошим кандидатом по привычности российским пользователям и покрытию. Но важная проверка официальных условий (ссылки в конце): для JavaScript API требуется API-ключ и надо соблюдать отображение логотипа/копирайта и другие ограничения. Официальная страница бесплатных условий прямо запрещает применять API для мониторинга/диспетчеризации и отслеживания транспорта в реальном времени; для такого сценария нужна коммерческая лицензия/согласование. Это относится к сути ULTrack даже если сайт волонтёрский или бесплатный. На тарифной странице при проверке 27.10.2026 для JS API отображались бесплатный объём до 500 запросов в сутки при соблюдении условий, коммерческий годовой тариф и отдельное отключение рекламы за 2 000 ₽/месяц или 20 000 ₽/год на один домен. Это лишь опубликованные на тот момент цифры, не готовая смета ULTrack: попросите Яндекс письменно подтвердить допустимость real-time tracking и расчёт для ожидаемой аудитории. Не подключайте бесплатный ключ в продакшен до такого подтверждения.

| Вариант | Плюсы | Что проверить |
|---|---|---|
| Leaflet + OSM-тайлы для разработки | Быстрый старт, независимая библиотека, нет ключа для локального прототипа | У общественного tile-сервера нет SLA; ограничения на нагрузку; для production нужен подходящий provider или self-host |
| Leaflet + коммерческий OSM provider | Можно оставить нашу логику маркеров и заменить только слой фона; есть поддержка/лимиты по договору | Сравнить покрытие Ульяновска, цену, SLA, права на реальное отслеживание и правила атрибуции/кэша |
| Яндекс JavaScript API | Интерактивная российская карта и API для браузера | API-ключ, сохранение брендинга карты, актуальная цена и обязательное коммерческое разрешение для real-time fleet tracking |
| 2GIS Map API / MapGL | Кандидат для сравнения покрытия и детализации Ульяновска; можно запросить demo key | Сервисы 2GIS предоставляются по лицензии; цену и допустимость живого отслеживания нужно уточнить у поставщика письменно |
| Собственные тайлы на базе OSM | Больше контроля, меньше зависимости от общего публичного сервера | Нужны серверы, место, импорт/обновление данных, рендеринг, мониторинг и техническая поддержка |

Перед выбором команда должна проверить руками несколько районов Ульяновска на телефоне: качество названий улиц, адресов, дорог, зумов и скорость загрузки. Для демонстрации карты не нужны маршруты общественного транспорта от провайдера — маршруты и метки ULTrack являются отдельными слоями наших данных.

Итог не «всем обязательно OSM» или «всем обязательно Яндекс». **Для прототипа** достаточно Leaflet + OSM tiles с соблюдением публичной политики. **Для публичного live-сервиса** наименее зависимый от поставщика интерфейс — Leaflet, но фон должен идти от провайдера, который письменно разрешает данный сценарий и даёт подходящие лимиты/SLA. Яндекс и 2GIS следует сравнить по фактическому качеству карты Ульяновска и коммерческому предложению; пока такого сравнения/разрешения нет, корректного победителя назвать нельзя.

## 3.3. Что именно сделано в этом проекте

Поток файлов такой:

```text
браузер открывает GET /
      ↓
applist/app/urls.py подключает main.urls для сайта и auth.urls для авторизации
      ↓
applist/main/urls.py находит path("", map_page)
      ↓
applist/main/views.py вызывает render(request, "main/map.html")
      ↓
main/templates/main/map.html создаёт страницу и <div id="map">
      ↓
браузер загружает Leaflet, main/map.css и main/map.js
      ↓
map.js делает GET по URL из data-api-url
      ↓
app/urls.py находит /api/demo/vehicles/
      ↓
main/views.py → JsonResponse([...demo coordinates...])
      ↓
map.js разбирает JSON и передвигает/создаёт Leaflet-маркеры
```

Назначение файлов:

- `applist/app/urls.py` — подключает URL-таблицы основных приложений.
- `applist/main/urls.py` — адреса главной страницы карты и демонстрационного API.
- `applist/main/views.py` — обработчики карты и JSON-ответа с учебными точками.
- `applist/main/templates/main/map.html` — HTML карты: заголовок, статус, область карты, подключение CSS/JS.
- `applist/main/static/main/map.css` — размер/цвет карты, панели и маркерных плашек.
- `applist/main/static/main/map.js` — Leaflet, `fetch()`, обработка JSON, обновление меток.
- `applist/main/tests.py` — проверки, что HTML и GET-API работают, а POST на демонстрационный endpoint отклоняется.
- `applist/auth/urls.py` и `applist/auth/views.py` — только адреса и обработчики входа/регистрации.

`{% load static %}`, `{% static ... %}` и `{% url ... %}` — Django template tags. Их обрабатывает Django **до** отправки страницы. Например, `{% url 'demo_vehicle_locations' %}` превращается в корректный путь. Не открывай `map.html` двойным щелчком как обычный файл: без Django эти шаблонные команды не обработаются. Открой сайт через `runserver`.

В браузере открой **Developer Tools** (`F12`):

- **Network → Fetch/XHR** — запрос `/api/demo/vehicles/`, код `200`, ответ JSON;
- запросы `/static/...map.css` и `/static/...map.js` — должны иметь код `200`;
- запросы `tile.openstreetmap.org/...png` — кусочки основы карты;
- **Console** — ошибки JavaScript или загрузки Leaflet.

## 3.4. Чего этот код не делает

- Не просит разрешение на геолокацию телефона.
- Не отслеживает реальных водителей.
- Не принимает координаты по POST и не сохраняет их.
- Не содержит учётных записей, назначений маршрутов и проверки права водителя.
- Не даёт прогноза времени прибытия.

Это намеренное разделение. Текущая цель — проверить, что карта, Django и обмен JSON соединены. Реальный сбор GPS нужно добавить после согласования согласия водителя, авторизации, серверной валидации, частоты обновления, срока хранения точек, HTTPS и выбранного поставщика карты.

# Часть 4. HTTP-команды и тестирование вручную

Из корня репозитория `ULTrack` команда Django запускается из `applist`, потому что там лежит `manage.py`:

```powershell
cd "C:\Учёба\Нейропроект\ULTrack\applist"
python manage.py check
python manage.py test
python manage.py runserver
```

Пока сервер работает:

1. Открой `http://127.0.0.1:8000/` — увидишь страницу и карту.
2. Открой `http://127.0.0.1:8000/api/demo/vehicles/` — увидишь JSON.
3. Нажми «Обновить точки» — браузер снова делает GET запрос.
4. Нажми на синий маркер — откроется popup с номером демо-маршрута.
5. Отключи сеть или останови Django — статус покажет, что сервер недоступен.

Код JavaScript проверяет HTTP status через `response.ok`; ответ `404` тоже технически может быть корректно доставлен, поэтому `fetch()` сам по себе не считает все не-2xx ответы исключением. Мы вручную выдаём понятную ошибку для `response.ok === false`.

## Формат API сейчас

Метод и адрес: `GET /api/demo/vehicles/`

Ответ: `application/json`, объект с `mode` и массивом `vehicles`. У каждой точки есть стабильный `id` (чтобы двигать старую метку, а не рисовать новые), `route_number`, `lat`, `lon`, `accuracy_m`, `updated_at` и `is_demo`.

Когда вместо демонстрационных точек появится база, лучше сохранить похожий контракт. Так JavaScript-часть карты не обязана знать, SQLite у вас или PostgreSQL и кто внутри команды написал endpoint.

# Самопроверка проектного решения

**Вопрос:** не называем ли мы учебные координаты настоящей геолокацией?
**Проверка/поправка:** нет — текст на странице, API (`mode: demo`, `is_demo`) и popup подчёркивают, что это вымышленные координаты.

**Вопрос:** не перепутали ли карту с передачей GPS?
**Проверка/поправка:** нет — Leaflet отвечает за визуализацию; сервер ULTrack отвечает за точки. Слой тайлов отдаёт фон карты. Реальное GPS-сообщение пока не реализовано.

**Вопрос:** не выбрали ли мы Яндекс только потому, что он знаком?
**Проверка/поправка:** нет — проверены официальные условия: для бесплатного использования есть ограничение на real-time мониторинг транспорта. Поэтому код демонстрации изолирован на Leaflet, а производственный поставщик остаётся командным и юридическим решением.

**Вопрос:** означает ли «OSM бесплатный», что можно безлимитно пользоваться их серверами тайлов?
**Проверка/поправка:** нет — лицензия открытых картографических данных и инфраструктура публичных тайлов — разные вещи. У общественных серверов best-effort, нет SLA и есть технические правила.

**Вопрос:** опубликован ли результат на удалённом сервере?
**Проверка/поправка:** нет. В целевой папке создаётся локальный коммит, но push на `origin` не выполняется. Исходная папка не редактировалась.
